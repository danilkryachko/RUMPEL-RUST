# ADR-002: GPU-driven voxel rendering roadmap

## Status
Accepted

## Context
RUMPEL RUST already has two voxel render paths:

- the default `surface_streaming` path, which is production-facing today: surface-aware heightmap regions, `VoxelQuadMaterial`, texture-array tiles, repeat UVs, LOD, async CPU mesh tasks, upload throttling, and profiling metrics;
- the opt-in GPU compute prototype, which dispatches `mesh_generator.wgsl` and writes a single chunk mesh into Bevy mesh buffers.

The producer wants the long-term engine direction to move toward GPU-driven terrain: compute meshing first, then packed quads, indirect rendering, GPU culling, and later hierarchical far-field representations. The current CPU surface path remains the baseline/old mode for visual and profiling comparison while the GPU path reaches parity.

## Decision
Use a phased GPU-driven migration instead of replacing the renderer in one step.

1. **Render mode boundary:** keep surface streaming as the default renderer. Use `RUMPEL_RENDER_MODE=surface` for the baseline and `RUMPEL_RENDER_MODE=compute` for the GPU prototype. The legacy `RUMPEL_COMPUTE_PROTOTYPE=1` remains accepted as an alias.
2. **Phase 1 - compute parity slice:** feed one real world chunk or small region into the compute mesher, keep the output contract explicit, and measure it against the surface path. This phase must not depend on MDI, SVO, or GPU culling.
3. **Phase 2 - GPU streaming queue:** expand from one chunk to a bounded queue of compute jobs with per-job counters, no hot-path readbacks, deterministic lifecycle rules for loaded/building/pending regions, GPU-owned output buffers, and a direct compute terrain render phase before compacting the ABI.
4. **Phase 3 - packed quads / vertex pulling:** move away from full Bevy vertex attributes when measured upload bandwidth becomes the bottleneck. Store compact quad commands and draw them through a custom material or render phase.
5. **Phase 4 - indirect rendering and GPU culling:** introduce indirect draw buffers only after GPU meshing owns stable buffers and counters. CPU should submit coarse work, while GPU culls and draws visible terrain.
6. **Phase 5 - far-field hierarchy:** evaluate SVO/SVDAG or raymarched far terrain after near-field edit semantics, block registry mapping, and chunk streaming are stable.

## Guardrails
- Do not reduce view radius to hide performance issues unless the producer explicitly asks.
- Do not make an experimental compute slice the default until it has visual parity, profiling data, and a safe comparison path.
- Do not add per-frame GPU readbacks to production terrain; use readbacks only for diagnostics or bounded profiling.
- Preserve data-driven block IDs, texture atlas tile mapping, and Lua worldgen boundaries.
- Keep `surface_streaming` and `VoxelQuadMaterial` intact while the compute path matures.
